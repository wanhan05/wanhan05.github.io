Modern AI is computationally bottlenecked not by raw CPU speed but by the ability to perform massive numbers of simple arithmetic operations in parallel — and then by the ability to move data to those operations fast enough to keep them busy. This writeup covers three interconnected topics: the hardware architectures designed to solve this problem, the software optimizations that extract maximum efficiency from that hardware, and the real-world cost — financial, energetic, and physical — of running these systems at scale.

Part 1 — Hardware Accelerators

GPUs: Graphics Processing Units

Originally designed for rendering graphics, GPUs turned out to be extraordinarily well-suited for deep learning because graphics and neural networks share the same core computational primitive: multiplying large matrices in parallel.

Architecture

A CPU has a small number of powerful cores (typically 8–64) optimized for sequential, low-latency computation with complex control flow. A GPU has thousands of much simpler cores — NVIDIA's H100 has 16,896 CUDA cores — designed to execute the same instruction on thousands of data points simultaneously. This is called SIMD (Single Instruction, Multiple Data) parallelism.

The key components relevant to ML:

  • CUDA cores / Shader processors — basic parallel compute units handling floating-point arithmetic
  • Tensor Cores — specialized matrix multiply-accumulate units introduced in NVIDIA's Volta architecture (2017). An H100 can perform 4 petaFLOPS of FP8 tensor operations
  • HBM (High Bandwidth Memory) — stacked DRAM sitting directly on the GPU die. The H100 has 80GB HBM3 with ~3.35 TB/s bandwidth
  • NVLink / NVSwitch — high-speed interconnects allowing multiple GPUs to share memory without going through the CPU

Why GPUs dominate ML

GPUs won the deep learning era largely by accident and ecosystem. NVIDIA's CUDA programming model (released 2007) gave researchers a relatively accessible way to write GPU kernels, and the ecosystem — cuDNN, cuBLAS, PyTorch, TensorFlow — built up around it over a decade. By the time specialized AI chips arrived, the CUDA moat was enormous. GPT-4, Gemini, LLaMA, and AlphaFold were all trained on NVIDIA GPU clusters.

Limitations

  • Memory wall — GPT-4 (~1.8T parameters) cannot fit on a single GPU. Multi-GPU training requires tensor, pipeline, and data parallelism with significant engineering overhead
  • Power consumption — an H100 draws up to 700W. A cluster of 10,000 H100s draws ~7 megawatts, comparable to a small power plant
  • Cost — H100s sell for $25,000–$40,000 each. Large training runs cost tens to hundreds of millions of dollars

TPUs: Tensor Processing Units

TPUs are Google's custom accelerators, built from the ground up for neural network workloads. The first TPU was deployed internally at Google in 2015.

Architecture — Systolic Arrays

TPUs are systolic array processors. A systolic array is a grid of processing elements where data flows rhythmically from cell to cell, with each cell performing a multiply-accumulate operation as data passes through. This is architecturally ideal for matrix multiplication: the matrix flows through the array and the result accumulates without ever writing intermediate values back to memory.

The TPU v4 chip features a 128×128 systolic array, HBM on-package, and custom interconnects allowing TPU pods — racks of thousands of chips connected in a 3D torus topology — to behave as a single massively parallel computer. Google's TPU v4 pods contain 4,096 chips connected this way. The torus topology means data can flow efficiently between any two chips without routing through a central switch.

Strengths and limitations

Because Google controls both the hardware and the primary framework (JAX/XLA), they optimize the full stack from silicon to model code — XLA compiles entire computation graphs to TPU instructions, eliminating Python overhead. TPUs are power-efficient and excel at dense matrix multiplication. Limitations: ecosystem lock-in (JAX/XLA native, PyTorch secondary), less flexibility for irregular computation patterns, and harder debugging under the XLA compilation model.

LPUs: Language Processing Units

LPUs are the newest entrant, coined and commercialized by Groq. The term is somewhat marketing-driven, but the underlying architecture is genuinely novel and distinct from both GPUs and TPUs.

Architecture — Deterministic Streaming

Groq's LPU is a deterministic, compiler-driven processor built around the Tensor Streaming Processor (TSP). The key insight: the largest bottleneck in transformer inference is not compute but memory bandwidth and latency — specifically, the cost of loading billions of model weights from DRAM on every forward pass.

Groq's solution: on-chip SRAM only (900MB per chip, no HBM or external DRAM), giving bandwidths in the range of tens of TB/s versus ~3 TB/s for HBM3. Every operation is statically scheduled at compile time — no runtime scheduler, no caches, no branch predictors. The chip is simpler and more efficient per area. For large models that don't fit on one chip, weights stream chip-to-chip in a pipelined fashion.

Performance and limitations

Groq achieves 500+ tokens per second on LLaMA-70B, compared to ~50–100 tokens/second on a single H100 — a genuine result for autoregressive token generation. Latency is highly predictable. Limitations: LPUs are not suited for training (backpropagation exceeds on-chip SRAM), model size requires many chips at scale (LLaMA-70B needs 150+ chips at 900MB per chip), and the ecosystem is nascent compared to CUDA.

The Broader Landscape

Cerebras WSE
Cerebras Systems

A single chip the size of an entire silicon wafer — 900,000 cores, 40GB on-chip SRAM. Designed for training large models without inter-chip communication bottleneck. The most extreme "put everything on chip" expression.

Graphcore IPU
Graphcore

Massively parallel processor designed around the idea that neural network computation is more like graph traversal than matrix multiply. Different memory model from GPUs. Traction in research settings.

SambaNova
SambaNova Systems

Reconfigurable dataflow architecture that compiles neural network graphs into spatially mapped dataflow programs — similar in philosophy to Groq but more flexible for irregular workloads.

AWS Trainium / Inferentia
Amazon Web Services

Amazon's in-house training and inference chips, designed to reduce cloud customer dependence on NVIDIA and lower cost per token for inference at scale.

The common thread: every architecture is attacking the same bottleneck from different angles. The cost of moving data between memory and compute is now the primary constraint in large-scale AI — whether by putting more memory on-chip (Cerebras, Groq), building faster interconnects (TPU pods), or making compute units smarter about reusing data (Tensor Cores, systolic arrays).

Part 2 — Optimizations in Computation

The Memory Wall and Why It Defines Everything

The processor is almost never the bottleneck. The bottleneck is almost always getting data to the processor fast enough to keep it busy. A modern GPU core can perform thousands of floating-point operations per clock cycle — but if the values it needs are sitting in DRAM rather than on-chip SRAM, it will stall, waiting for data across a memory bus that is orders of magnitude slower than the compute units themselves.

The memory hierarchy is brutally tiered: registers under a nanosecond, L1 cache a few nanoseconds, DRAM roughly a hundred nanoseconds. For a GPU doing matrix arithmetic, that gap is the difference between peak utilization and idle silicon. Large language models — with parameter counts in the tens to hundreds of billions — absolutely cannot fit their weights in cache. Every forward pass requires pulling weights from DRAM or, in distributed settings, from across a network. The cost of that data movement frequently exceeds the cost of the computation itself.

Hardware Optimizations

Reduced precision arithmetic

The most impactful hardware optimization has been the shift toward lower-precision arithmetic. Operating in float16 rather than float32 cuts memory bandwidth requirements roughly in half — twice as many weights transferred per second. NVIDIA reports 2–3× speedup in mixed-precision training, where float16 handles the bulk of computation while float32 is reserved for gradient accumulation. At inference time, quantizing weights to INT8 or INT4 can reduce model size by 4–8×, enabling models that would otherwise require multiple GPUs to fit on a single device.

A Tensor Core on an H100 is not a general-purpose floating-point unit — it is a matrix-multiply-accumulate unit performing A × B + C on small matrix tiles in a single clock cycle, without the sequential bottleneck of a Von Neumann pipeline.

High-Bandwidth Memory (HBM)

Because bandwidth is the bottleneck, chip designers invested in HBM — a stacked memory architecture where DRAM dies are placed directly on the GPU die and connected through thousands of parallel wires (through-silicon vias). An H100 has roughly 3.35 TB/s of HBM3e bandwidth, compared to ~50 GB/s for consumer DDR5. That 60× difference is the reason a data center GPU costs tens of thousands of dollars while the rest of the system is comparatively cheap.

Tiled matrix multiplication and cache layout

A GPU's shared memory — the on-chip SRAM acting as an explicitly managed L1 cache — is tiny: typically 48–192 KB per streaming multiprocessor. A model with billions of parameters will never fit there. What does fit is a tile of the weight matrix currently being multiplied. Tiled matrix multiplication restructures computation to load a tile of A and a tile of B into shared memory, perform all multiplications involving those tiles, and only then load the next tiles — the same principle as i-k-j loop reordering for cache efficiency, extended to the GPU's explicit memory hierarchy. cuBLAS and cuDNN implement these kernels with hand-tuned assembly.

Software Optimizations

Flash Attention

Flash Attention restructures the entire attention computation to keep intermediate activations in SRAM rather than writing them back to HBM between operations. A naive implementation of a transformer layer executes attention scores, softmax, dropout, and projection as four separate kernels — each requiring a round trip to HBM. Flash Attention performs all operations on a single tile of data while it is resident in SRAM: reading from HBM once, writing back once. For models processing sequences of tens of thousands of tokens, this is the difference between the computation being feasible and prohibitively expensive.

Operator fusion

Operator fusion combines multiple mathematical operations into a single GPU kernel. The GELU activation after a linear layer, the layer normalization before an attention block, the residual addition that follows — all can be fused when the compute graph is known statically, eliminating redundant memory traffic at the cost of more complex kernel code.

Static compilation — XLA and torch.compile

Static compilation of compute graphs allows the runtime to reason about the entire computation before executing any of it. This enables constant folding (precomputing results known at compile time), dead code elimination (removing unused operations), and layout optimization (choosing tensor storage orders globally to minimize transposes). XLA, the compiler used by JAX and TensorFlow, generates fused kernels targeting specific hardware backends — often competitive with hand-tuned cuBLAS kernels while being far easier to deploy across different hardware targets.

Batching and the throughput-latency tradeoff

A model serving a single request pays the full memory bandwidth cost of loading weights for each request independently. Batching multiple requests together amortizes those weight reads: weights are loaded once and the same matrix multiplication serves multiple inputs simultaneously. This is the fundamental production inference tradeoff — larger batches improve throughput at the expense of latency. Systems like vLLM implement continuous batching, dynamically adding requests to in-progress batches to recover throughput while keeping tail latency manageable.

Speculative decoding

A small fast draft model proposes multiple tokens at once, which the large model then verifies in a single parallel forward pass. Verification is computationally cheaper than generation, reducing wall-clock inference latency by 3–5× with no change in output quality. It is effectively a prefetching strategy applied at the token level — the same principle that cache prefetching applies at the memory level, one abstraction layer higher.

Distributed parallelism strategies

A 70B parameter model requires ~140GB in float16 — far exceeding a single A100's 80GB. Three strategies compose to handle this:

  • Data parallelism — replicate the model across devices, split the batch. Synchronize gradients after each backward pass via all-reduce, overlapped with the backward pass on subsequent layers
  • Tensor parallelism — split individual weight matrices across devices. Requires all-reduce communication inside each layer
  • Pipeline parallelism — assign different layers to different devices, pass activations forward and gradients backward. Requires careful scheduling to avoid idle "bubble" time

For very large models, these strategies are composed in three dimensions: Megatron-LM and DeepSpeed combine all three, mapping computation onto cluster interconnect topology — fast NVLink within a node, slower InfiniBand across nodes.

Part 3 — The Real Cost of Compute at Scale

What Training a Large Model Actually Costs

GPT-3 has 175 billion parameters and was trained on roughly 300 billion tokens. The total compute required is approximately 3.14 × 10²³ floating-point operations — about 314 zettaFLOPs. Training ran on roughly 10,000 NVIDIA V100 GPUs for several weeks. A V100 delivers approximately 125 teraFLOPS in mixed precision. Accounting for hardware utilization (rarely above 30–50% due to communication overhead, memory bandwidth limits, and scheduling inefficiency), a realistic estimate puts actual wall-clock training time at around 34 days on that cluster. The electricity cost alone runs into the millions of dollars.

The scaling laws research from Hoffman et al. (the Chinchilla paper) established that compute-optimal training requires scaling training tokens proportionally with model parameters — roughly 20 tokens per parameter for a given compute budget. This means that doubling model size without doubling training data produces a suboptimal model. Correctly calibrated, the compute requirement scales roughly with the product of parameters and training tokens — meaning achieving a given quality level requires quadratically increasing investment as the performance frontier advances.

Memory Bandwidth as the Inference Bottleneck

At inference time, the structure shifts. A forward pass through a 70B parameter model in float16 requires reading roughly 140GB of weights from memory for each token generated. Generating a 1,000-token response therefore requires reading 140 terabytes of data from DRAM — for one user request. On an A100 with 2 TB/s of HBM bandwidth, that implies a floor of 70 seconds simply for memory access, ignoring compute entirely, when serving a single request.

This is why inference is almost universally memory-bandwidth-bound rather than compute-bound for autoregressive generation. The key ratio is arithmetic intensity — FLOP/byte. For matrix-vector multiplication (token-by-token generation), arithmetic intensity equals approximately the batch size. Serving a single request has arithmetic intensity of 1, far below the hardware's compute-to-bandwidth ratio (~300 FLOP/byte on an A100). Only when batch sizes reach into the hundreds does the computation become compute-bound and the hardware fully utilized.

Cloud Economics at Scale

An EC2 p4d.24xlarge instance — 8 A100 GPUs, 96 vCPUs, 1.1TB of memory — costs roughly $32/hour on-demand. Training a frontier model for 30 days on a cluster of 1,000 such instances costs approximately $23 million in raw compute alone, before reserved instance discounts, egress fees, storage costs, and the labor of engineering and debugging the training run.

At inference scale, economics shift toward utilization efficiency. A single A100 instance serving a 70B parameter model handles perhaps 5–20 requests per second depending on sequence length and batch size. A system serving millions of users requires thousands of such instances, with load balancing, autoscaling, and capacity planning that mirrors multiprocessor scheduling — matching available compute to fluctuating demand without stranding expensive GPU capacity or degrading user-facing latency.

The Efficiency Frontier

The practical work in ML systems is not maximizing a single metric but navigating a multi-dimensional tradeoff between accuracy, latency, cost, energy consumption, and deployability. A model achieving 95% benchmark accuracy but requiring $10M of compute per inference cluster is not competitive with one achieving 90% at $1M for most applications. Quantization, distillation, pruning, and speculative decoding are all points on this surface — techniques that trade a small amount of model quality for large reductions in compute or memory requirements.

The trajectory is clear: as models grow larger and the gap between compute capacity and memory bandwidth widens, the systems-level work of efficiently mapping computations onto hardware becomes as important as the algorithmic work of designing the models themselves.
